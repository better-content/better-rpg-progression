## Shipped gameplay contract in this source

The mod provides a server-owned, per-Life RPG allocation ledger and eight JSON-defined build identities (`src/main/resources/data/better_rpg_progression/stats/{aerialist,artisan,sharpshooter,skirmisher,spellcaster,survivalist,trailblazer,vanguard}.json`). Server ticks grant one point for each newly reached experience level above the player's Life peak; login baselines existing players to their current level rather than retroactively awarding points (`PointAwarder.kt`, `CommonForgeEvents.kt`). Players open the stats UI with **O** (`client/input/Keybinds.kt`), choose manual allocations or a durable ordered automatic plan, and the server validates allocations and syncs the outcome (`C2SApplyStats.kt`, `C2SAutoAllocationPlan.kt`, `AllocationPolicy.kt`, `Network.kt`). At final death the current Life points/allocations are reset while auto-plan preferences persist; ordinary non-death clone preserves the ledger (`PlayerStats.kt`, `CommonForgeEvents.kt`). Stat projections include movement, combat and survival effects, with optional integrations gated by loaded mods (`StatAttributeProjector.kt`, `EffectAvailability.kt`, `RpgStatsMod.kt`). This is not a claim that every optional projection works in the selected pack.

**Item/block acquisition and usage references:** `ModItems.kt` registers `better_rpg_progression:heart_fragment` (stackable) and the legacy `better_rpg_progression:still_beating_heart`; `ModBlocks.kt` registers `better_rpg_progression:heart_block` and its item. `CommonForgeEvents.kt` captures a final-death level before other death handlers change XP, finalizes a Blood Magic-gated fragment entitlement only after uncanceled death, transfers it on clone and delivers pending fragments into inventory on respawn/login/player tick (one stack of at most 64 per tick, no dropped overflow entities). `HeartFragmentEntitlements.kt` defines durable pending/delivery behavior and legacy personalized-heart conversion. `HeartBlock.kt` consumes a held fragment on successful server-side use to permanently install it; `HeartBlockEntity.kt` saves the count and requests LP from the first adjacent Blood Magic altar each tick. `HeartBlockItem.kt` carries installed-count data; `data/better_rpg_progression/loot_tables/blocks/heart_block.json` defines block drops. No recipe JSON exists under this repository's `src/main/resources/data`; the source alone does **not** establish a survival crafting root for the heart block. A full-pack recipe/root and actual Blood Magic availability must be checked separately. `StillBeatingHeartAltarHandler.kt` contains historical altar-slot code, but `CommonForgeEvents.onLevelTick` explicitly does not invoke its generator; do not present that retired path as a current acquisition method. Item commands for controlled qualification: `/give @s better_rpg_progression:heart_fragment` and `/give @s better_rpg_progression:heart_block` are debug acquisition, not evidence of survival availability.

JVM tests inspect policy/NBT/presentation, not live interactions. Extend native coverage in a separately reviewed change and update the fixture's exact count when adding required GameTests; do not imply the current six cover those paths. The strengthened JVM save round-trip only verifies an in-memory NBT boundary, not disk reload.
2. **Full-pack/recipe root:** inspect candidate build-69 manifests, artifact hashes and all pack-defined recipes, loot and configuration for legitimate survival acquisition, required mod providers, registry compatibility and progression blockers. Run pack gameplay/recipe-root/GUI/scale suites only after human execution approval and authoring review. A local `verifyFull` cannot substitute for installed-binary pack checks.

Review upgrades on a copy of an existing world before any shared-world migration; never assume a reset is acceptable. Sample one world per exact candidate (default seed **424242**) rather than pooling outcomes across builds.
